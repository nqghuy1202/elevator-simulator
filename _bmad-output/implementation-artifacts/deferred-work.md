- source_spec: `_bmad-output/implementation-artifacts/spec-1-3-pending-call-re-evaluation.md`
  summary: An idle elevator sitting exactly at a floor with two opposite-direction pending Hall Calls for that same floor can be selected twice in one `reevaluatePending()` pass, causing one harmless-but-unnecessary extra door-open/dwell cycle before settling Idle.
  evidence: Root cause is in Story 1.1's `IdleState`/`DoorOpenState` same-floor immediate-open fix, which never updates `direction` away from `'IDLE'` — so the elevator stays `IDLE`-eligible (any direction) for a second pending call at the same floor. Traced end-to-end: functionally harmless (the floor is still served correctly, no call is lost or mis-served), but an observable inefficiency. Reachability requires a narrow, compound trigger (two opposite-direction pending calls at the exact floor an idle elevator already occupies) not exercised by Story 1.3's own scope. Flagged for Story 1.4 (Stop Queue Integrity), which already owns related same-floor/queue invariants.

- source_spec: `_bmad-output/implementation-artifacts/spec-3-2-frontend-container-nginx-compose-orchestration.md`
  summary: `docker-compose.yml` has no healthcheck/restart policy; `frontend` uses plain `depends_on: [backend]` (start-order only, not "wait until healthy").
  evidence: Not a functional bug today — Nginx only proxy-connects to `backend` when a client actually requests `/socket.io/`, so a slow-starting backend doesn't cause a startup failure, and this repo's containers start in well under a second. Would matter if the backend's startup time ever grew (e.g. a future migration/seed step) and a client raced it. Adding healthchecks/restart policy is reasonable production hardening, but the epic explicitly scopes this story to a lean, proportionate demo setup and this isn't required by any acceptance criterion.

- source_spec: `_bmad-output/implementation-artifacts/spec-2-3-hall-call-pending-indicator-ui.md`
  summary: When a Hall Call is satisfied via the "piggyback" paths (a floor already queued for another reason, or an elevator already stationary there with doors open), `Dispatcher.tryAssign` still treats `assignHallCall`'s `false` return as unassigned and pushes it into `Dispatcher.pendingCalls` — even though Story 2.3's `activeHallCalls` tracker correctly drains it right away. `pendingHallCalls` can then carry, and `reevaluatePending()` can churn, a stale entry for a call that's already been serviced, occasionally causing one spurious extra door-open when the elevator later goes idle at that same floor.
  evidence: Traced by two independent review lenses to pre-existing `Dispatcher`/`Elevator.insertStop` behavior from Story 1.3/1.4 (commits `04bd8bc`/`b21eac1`) — Story 2.3's diff never touches `Dispatcher.tryAssign`'s success/pending routing, `addPending`, or `reevaluatePending`. Explicitly out of scope per Story 2.3's own frozen boundary ("No behavior or shape change to `pendingHallCalls`"). No current frontend code reads `pendingHallCalls` — only `activeHallCalls` drives the Hall Call indicator — so there is no observable UI-facing bug today, only an internal data inconsistency and an occasional harmless extra door-open cycle.
